# 개발과 배포

[로컬 실행 방법](../README.md#시작하기)에 따라 개발 서버를 시작합니다. Vite와 Vercel은 같은 읽기 전용 API 핸들러를 사용합니다. 실데이터를 조회하는 환경에서는 `api.github.com`에 접근할 수 있어야 합니다. GitHub 조회 코드는 요청을 분기하는 `server/github.ts`와 기능별 `server/github-*.ts`로 나뉩니다.

| 작업                           | 위치                                                      |
| ------------------------------ | --------------------------------------------------------- |
| GitHub 요청과 캐시             | [server/github.ts](../server/github.ts)                   |
| GitHub 기록에서 작업 상태 판정 | [server/model.ts](../server/model.ts)                     |
| API 진입점                     | [api/github.ts](../api/github.ts)                         |
| 앱 진입점과 전체 상태          | [src/main.tsx](../src/main.tsx)                           |
| 왕국 지도                      | [src/kingdom-region.tsx](../src/kingdom-region.tsx)       |

## 검증

```bash
npm test
npm run build
npm run format:check
```

### 화면 테스트

```bash
npx playwright install chromium # 처음 한 번
npm run test:ui
```

[e2e/](../e2e)의 테스트는 빌드 결과물을 Chromium에서 열어 왕국 표시, 상세 창, 저장소·토큰·표시 모드 설정, 예외 상태, 화면 폭별 배치, 갱신 요청 수를 확인합니다. GitHub 요청은 모두 [e2e/fixtures.ts](../e2e/fixtures.ts)의 고정 응답으로 대체하므로 토큰이나 네트워크 없이 실행됩니다. 응답 구조를 바꾸면 고정 응답이 `npm run build`의 타입 검사에 걸립니다.

화면에 새 동작을 추가하면 해당 흐름의 테스트를 함께 추가합니다. 요청이 없어야 함을 확인할 때는 뒤이은 요청이 도착한 다음에 요청 기록을 비교합니다.

PR과 `dev` 푸시에서는 [CI](../.github/workflows/ci.yml)의 **UI test** 작업이 [변경 경로](../.github/scripts/ui_test_scope.py)를 보고, 화면에 영향을 주는 파일(`src/`, `server/`, `api/`, `assets/`, `e2e/`, 빌드 설정)이 바뀐 경우에만 브라우저 테스트를 실행합니다. 그 밖의 변경에서는 테스트 단계를 건너뛰고 성공으로 끝납니다. **Test and build**와 같은 워크플로이므로 AI completion은 두 작업이 모두 통과한 뒤에 머지합니다.

## Vercel 배포

GitHub 저장소를 Vercel에 연결하고 Node.js 24 기반 Vite 프로젝트로 배포합니다. 빌드 명령과 출력 경로는 [vercel.json](../vercel.json)에 있습니다. 별도 DB는 필요하지 않습니다.

Git 연동은 `main`을 프로덕션으로, `dev`를 프리뷰로 자동 배포합니다. 같은 저장소의 다른 브랜치는 열린 PR에 `preview` 라벨이 있거나, GitHub가 그 PR로 종료될 것으로 연결한 같은 저장소 이슈에 `preview` 라벨이 있을 때 [프리뷰 워크플로](../.github/workflows/vercel-preview.yml)가 배포합니다. PR 생성 후 라벨을 추가하거나 새 커밋을 푸시해도 적용됩니다. 라벨을 제거하면 이후 커밋은 다시 현재 라벨을 기준으로 판정합니다. 기존 배포는 유지됩니다.

**Settings → Environments → vercel-preview**에서 배포를 허용할 브랜치로 `dev`와 `main`을 지정하고 Agentopia에 배포할 수 있는 팀 토큰을 환경 시크릿 `VERCEL_TOKEN`으로 등록합니다. 같은 토큰을 저장소 시크릿에도 등록했다면 환경으로 이전한 뒤 저장소에서 제거합니다. PR 대상 이벤트에는 기준 브랜치가 적용됩니다. 러너는 기본 브랜치의 스크립트로 PR의 최신 커밋을 확인하고 Vercel에 빌드를 요청합니다. PR 검사 목록의 **Vercel Preview URL → Details**에서 해당 커밋의 프리뷰를 열 수 있습니다. 이 검사의 성공은 URL 발급을 의미합니다. 빌드 완료 여부는 Vercel에서 확인합니다.

저장소의 [main 룰셋](../.github/rulesets/main.json)을 적용하면 `main` 대상 PR은 Vercel 프리뷰 검사를 통과해야 머지할 수 있습니다. 작업 및 PR 작성 규칙은 [개발 지침](../AGENTS.md)을 따릅니다.

## 프로덕션 릴리스 기록

기본 브랜치 `dev`의 [릴리스 워크플로](../.github/workflows/production-release.yml)는 Vercel이 Agentopia의 `main` 프로덕션 배포 성공을 통지하면 실행됩니다. 배포한 커밋마다 `prod-<전체 커밋 SHA>` 태그가 남습니다. 같은 커밋을 다시 배포하면 기존 태그를 사용합니다.

GitHub Releases에는 이 워크플로가 발행한 최신 성공 릴리스 하나를 유지합니다. 새 릴리스 발행에 성공한 뒤 이전 자동 릴리스 항목을 삭제하며, 이전 커밋은 Tags에서 확인할 수 있습니다. 프리뷰·실패 이벤트와 수동 릴리스는 정리 대상에서 제외됩니다.

### 배포는 성공했는데 태그가 없을 때

1. GitHub Actions의 **Production release** 실행 목록을 확인합니다. 실행이 없다면 Vercel 프로젝트의 **Settings → Git**에서 `repository_dispatch` 이벤트 전송을 확인합니다. 프로젝트 API에서 `gitProviderOptions.disableRepositoryDispatchEvents` 값이 `false`여야 합니다. GitHub 커밋에 표시되는 Vercel 성공 검사와 이 이벤트는 별도로 전달됩니다.
2. 실행이 있으면 작업의 실행 여부와 로그를 확인합니다. 워크플로는 Vercel 봇이 보낸 이 프로젝트의 `production` 환경, `main` 브랜치 성공 이벤트만 처리합니다. 발행 단계에서 실패한 실행은 원인을 해결한 뒤 다시 실행할 수 있습니다.
3. 이미 누락된 태그를 복구할 때는 Vercel에서 프로덕션 도메인이 연결된 성공 배포의 **전체 Git SHA**를 확인합니다. GitHub의 Tags에서 해당 태그가 없는지 확인한 뒤 그 SHA에 `prod-<전체 SHA>` 태그를 생성합니다. 이 복구는 Git 태그만 만들며, 자동 릴리스 발행 여부는 다음 프로덕션 성공 이벤트의 실행 기록에서 확인합니다.

## 이슈에서 AI 초안 PR 만들기

저장소 쓰기 권한이 있는 사용자가 열린 이슈에 `ai:develop` 라벨을 붙이면 Codex가 변경을 준비하고 Claude가 해당 커밋을 리뷰합니다. `ai:develop:claude`를 단독으로 붙이면 Claude가 개발하고 Codex가 리뷰합니다. 이슈마다 `ai/issue-<번호>-<개발자>` 브랜치와 `dev` 대상 초안 PR 한 개를 사용합니다. 변경 범위는 `src/`, `server/`, `docs/`의 Markdown·TypeScript·CSS와 `README.md`입니다. `api/`에서는 기존 파일의 내용만 수정할 수 있습니다. 화면 동작이 바뀌면 기존 `e2e/*.spec.ts`의 검증도 함께 수정할 수 있습니다.

- 모델이 제안한 제목만 저장소 형식을 벗어나면 같은 검사를 통과한 이슈 제목을 커밋과 초안 PR에 사용합니다. 개발 완료 응답의 요약이나 편집 개수 등이 형식 검증에서 거부되면 남은 호출 예산 안에서 같은 근거로 한 번 교정합니다. 교정도 실패하면 게시 전에 중단하고 어떤 제한에 걸렸는지 기록합니다.
- 개발안은 게시 전에 같은 HEAD의 파일에 순서대로 적용해 검증합니다. 원문이 없거나 여러 곳과 일치하는 경우 남은 개발 호출 예산 안에서 파일을 다시 읽고 전체 편집안을 한 번 교정할 수 있습니다. 재검증에 실패하면 이슈에 편집 순번과 사유를 기록합니다. 허용 범위를 벗어나는 편집은 즉시 중단합니다.
- 화면 문구나 심볼은 파일 안에서 검색해 해당 줄부터 읽을 수 있습니다. 한 번에 요청한 탐색이 한도를 넘으면 허용된 호출의 결과와 생략한 호출을 모델에 돌려줍니다. 전체 탐색 한도를 소진하면 수집한 근거로 결과를 제출하거나 부족한 근거를 설명합니다.
- 리뷰 탐색이 길어져도 마지막 호출은 결과 형식 교정에 쓸 수 있도록 남겨 둡니다. 교정 요청에는 위반한 필드와 제한을 알려 주며, 기존 수정 요청이나 지적을 교정 중 승인으로 바꾸면 게시 전에 중단합니다.
- 담당 리뷰어가 수정을 요청하면 같은 PR에서 개발자가 의견을 반영하고 새 커밋을 다시 검토합니다. 자동 수정은 최대 두 번이며, 적용할 변경이 없거나 한도에 도달하면 이슈에 사유를 남깁니다. 리뷰에서 직접 사람의 판단을 요청한 경우에는 즉시 중단합니다.
- 개발 변경에는 게시 전에 저장소의 Prettier 설정을 적용합니다. 문법 오류가 있으면 해당 파일과 위치를 개발 모델에 전달해 한 차례 교정을 요청합니다. 리뷰를 승인 상태로 기록한 실행은 이슈 번호와 실행 번호를 전달해 완료 워크플로를 직접 시작합니다. 담당 리뷰어의 리뷰와 같은 커밋의 PR CI(**Test and build**와 **UI test**)가 통과하면 **AI completion**이 초안을 검토 준비 상태로 전환하고 dev에 스쿼시 머지합니다. 머지가 확인되면 이슈를 completed로 닫습니다. 완료 단계만 재시도하려면 AI completion에서 이슈 번호로 수동 실행합니다. PR CI는 모델 키와 게시 토큰 없이 실행됩니다.
- 이슈의 개발 담당 라벨을 유지한 상태에서 **AI development → Run workflow**에 이슈 번호를 입력하면 기존 초안을 이어서 처리합니다. 다른 이슈의 머지로 `dev`가 앞서면 아래 기준으로 자동 복구합니다. 이슈를 닫거나 `ai:stop`을 붙이면 다음 게시 단계에서 실행을 중단합니다.
- **Issues → Labels**에서 `ai:develop`, `ai:develop:claude`, `ai:stop`을 만듭니다.
- Actions에 `ai-development` 환경을 만들고 배포 브랜치를 `dev`로 제한합니다. 환경 시크릿에 `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `AI_AUTOMATION_TOKEN`을, 환경 변수에 `AI_CODEX_MODEL`, `AI_CLAUDE_MODEL`을 설정합니다. 게시 토큰은 Agentopia 저장소의 Contents 및 Pull requests 쓰기 권한을 가진 GitHub App 토큰 또는 fine-grained PAT가 필요합니다. 기준 갱신 push에 이미 dev에 반영된 워크플로 파일 변경이 포함되어 GitHub가 권한 오류를 반환하면 해당 토큰의 Workflows 쓰기 권한도 확인합니다. 별도 게시 토큰을 사용해야 PR 이벤트에서 일반 CI가 시작됩니다.
- 비공개 저장소로 전환하면 Git 커밋 조회에도 Actions의 Contents 읽기 권한이 필요합니다. 워크플로는 커밋을 가져오는 명령에만 이 자격 증명을 전달합니다.

환경의 **Deployment branches and tags → Selected branches and tags**에 브랜치 `dev` 하나만 등록합니다. 개발·완료 워크플로는 비밀을 사용하는 단계 전에 이 설정을 조회합니다. 조회 실패도 중단 사유입니다. 실제 접근 경계는 GitHub 환경 설정에서 강제해야 합니다.

개발과 CI 완료 단계는 이슈 번호별로 같은 큐에서 진행 댓글 하나를 갱신합니다. 맨 위에 현재 상태와 사유를 표시하고 아래에는 실행 차수별로 주요 변경과 당시 PR·Actions 링크를 남깁니다. 기존 댓글은 다음 갱신 때 마지막 확인 상태부터 이력을 이어 씁니다. 댓글 길이 한도에 가까워지면 오래된 실행 이력부터 줄이고 현재 체크포인트를 유지합니다. CI 시간 초과·취소·재실행은 이력에 기록하고 승인 상태를 유지하므로 CI가 통과하면 완료 워크플로를 다시 실행할 수 있습니다. 커밋별 리뷰 본문은 PR에 유지하며, 머지와 이슈 종료를 각각 확인한 뒤 완료를 기록합니다.

상태 댓글은 `schemaVersion`, 실행/이슈 번호, 단계와 사유, 게시 후 HEAD를 포함합니다. `ready`는 현재 HEAD의 독립 리뷰 승인과 CI 대기, `recovering`은 기준 변경 복구입니다. `revising`에서 복구 예약이 `development` 또는 `format`이면 실행 사유와 실패한 CI를 함께 확인합니다. 명시적 중단과 수동 변경은 사유가 있는 `needs_human`으로 기록합니다. 최종 머지와 해결 여부는 GitHub PR과 이슈의 실제 상태로 확인합니다.

월드맵은 같은 이슈에서 봇 기록의 실행 ID와 시도가 일치하는 진행 중 실행을 후속 대기 실행보다 우선합니다. 별도 실행의 성공만으로는 기록된 실패나 사람 확인 요청을 해제하지 않습니다. 역할 필드가 없을 때는 현재 시도 시작 이후에 생성된 같은 봇 댓글의 Markdown 또는 접힌 HTML `진행 기록` 목록을 확인하며, 일반 댓글이나 생성 서명으로 담당자를 추정하지 않습니다.

PR 복구 상태를 소비할 때는 다음 필드를 대조합니다.

- `issue`, `pullNumber`, `head`는 작업 대상이고, `runId`와 `attempt`는 상태를 작성한 **개발 실행**입니다. 실패한 CI는 같은 저장소의 PR과 HEAD에 연결된 CI 실행에서 별도로 확인합니다.
- `recovery.ciRepairs`는 일반 CI 수정에 사용한 시도 수입니다. 포맷 전용 시도는 `recovery.formatRepair`로 따로 기록합니다. 두 값은 이후 단계에도 남을 수 있습니다. `recovery.pending`은 현재 예약된 작업이며 일반 리뷰 수정 때도 `development`가 될 수 있습니다.
- CI 수정 예약 시 `recovery.ciRepair`에 실패한 HEAD, CI 실행 ID/시도 번호, 개발 실행 ID와 복구 시도 수·한도를 기록합니다. 이전 기록에 연결 정보가 없으면 수정 중인 것으로 추정하지 않습니다.
- CI 수정 커밋을 게시하면 `recovery.ciReviewHead`에 새 SHA를 기록합니다. 후속 HEAD의 CI를 확인할 때 이 값과 실제 PR HEAD를 대조합니다. 시도를 예약한 시점에는 아직 새 SHA가 없습니다.
- `status: needs_human`은 사람 확인 요청이며 `reason`에 사유가 있습니다. `failed`는 개별 실행 실패를 포함합니다. 시도 수나 실패한 이전 실행만으로 최종 중단을 확정하지 않습니다. 현재 체크포인트에는 모든 단계에 걸친 원본 실패 CI 실행 ID와 총 시도 한도가 항상 제공되지는 않습니다.
- 이슈와 PR은 두 모드에서 같은 배지를 사용합니다. 확인된 실행·재시도 대기는 노란 일시정지, 사람 확인은 물음표, 확인된 실행 실패는 빨간 정사각형입니다. CI나 개발 실행 하나가 실패했을 때 툴팁에는 ‘실행 실패’와 사유를 표시합니다. 배지를 캐릭터 오른쪽 위에 두고 파티가 비면 이슈·PR 아이콘에 표시합니다. 재시도가 시작되면 대기 배지를 지우고 실제 담당 캐릭터가 움직입니다. PR은 현재 HEAD와 연결된 복구 기록을 사용하며 사유는 툴팁과 접근성 이름으로 확인합니다.

개발·리뷰는 각각 대화당 최대 15턴이며 이슈당 모델 대화는 누적 20회입니다. 수동 재개도 같은 한도를 사용하며, 소진하면 담당자가 기존 PR을 이어서 처리합니다. 기존 체크포인트는 이 필드가 처음 기록되는 시점부터 누적합니다. 개발의 `in_progress`는 같은 대화에서 이어가고 최종 편집안만 게시합니다. `needs_human` 사유가 `progress` 같은 중간 점검 문구뿐이면 설명만 한 번 요청합니다.

### 병렬 작업 중 기준 브랜치 갱신

- 게시 전에는 기존 수정안을 폐기하고 새 `dev`의 코드와 AGENTS.md로 한 번 다시 시작합니다. 작업 브랜치를 게시한 뒤에는 새 기준을 최대 두 번 일반 병합으로 반영합니다. PR 생성 전까지 확인된 커밋과 PR 설명을 보관하고 같은 브랜치에서 이어갑니다.
- Git 자동 병합이 충돌하면, 작업이 허용된 일반 텍스트 파일 하나의 한 줄 교체이고 최신 파일의 같은 위치에 원문이 유일하게 남아 있을 때만 기존 편집 검증기로 재적용합니다. 이 시도는 이슈당 한 번입니다. 변경 위치가 겹치거나 한도를 소진하면 이슈에 사람 확인 요청을 표시합니다.
- GitHub Actions 봇의 이슈 상태 댓글에 기준·작업 커밋, 이슈 및 PR 식별 정보, 시도 횟수와 진행 중인 작업을 기록합니다. 모델 호출과 쓰기는 예약을 기록한 뒤 수행합니다. 이슈 내용이나 PR·작업 HEAD가 달라지거나, 게시·리뷰 결과가 확정되지 않은 경우에는 자동 재실행을 중지합니다. 이전 버전의 상태에는 복구 식별 정보가 없어 사람이 확인해야 합니다.
- 완료 단계는 검토한 HEAD의 PR CI를 확인합니다. 대기 중이나 머지 직전 기준 변경을 감지하면 GitHub Actions 토큰의 Actions 쓰기 권한으로 같은 이슈의 개발 워크플로를 호출합니다. 갱신된 HEAD에 리뷰와 CI가 다시 필요합니다. 과거 CI의 결과는 Actions 실행 이력에 남고 이슈의 현재 상태에는 복구 단계가 표시됩니다.

### 실행을 재개할 수 없을 때

- 기존 초안 PR을 닫았다면 같은 PR을 다시 열고, 이슈를 연 상태에서 AI 워크플로를 재실행합니다. 이미 머지된 작업의 후속 변경은 새 이슈로 시작합니다.
- 모델 통신 실패, 실행 중단 또는 기준 갱신 한도 도달 후에는 이슈 내용과 작업 브랜치 HEAD, 초안 PR 및 리뷰 댓글을 확인합니다. 쓰기 권한 사용자가 **AI development → Run workflow**에서 `dev`와 이슈 번호를 선택하고 `recovery_run`을 비워 새 실행을 시작하면, 저장된 게시 상태와 실제 상태가 일치할 때 예약과 한도를 초기화합니다.
- 리뷰 댓글 게시 응답이 유실되면 수동 재개 시 같은 PR·HEAD에서 신뢰된 봇 댓글과 예약 시 저장한 본문 해시를 대조합니다. 일치하면 검토 결과를 복원하고, 게시 여부가 확인되지 않으면 중단합니다. 기존 커밋과 리뷰를 확인해 해당 PR을 수동으로 마무리하거나 남은 작업을 새 이슈로 분리합니다. 기록된 브랜치를 삭제하면 저장된 HEAD와 일치하지 않습니다.

모델 통신과 편집 검증 코드 일부는 [Commit Trail](https://github.com/han41858/commit-trail)에서 가져왔으며 해당 폴더에 [원본 MIT 고지](../.github/scripts/ai-development/LICENSE.md)를 포함합니다.

화면에 영향을 줄 수 있는 소스나 테스트를 변경하면 개발자와 리뷰어가 각자 관련 Playwright 테스트 본문을 읽고 역할·접근성 이름·클릭 동작을 대조합니다. 화면 문구·툴팁·조작이 달라지면 이전 동작을 기대하는 검사와 새 동작 검증을 같은 PR에 반영합니다. 수정한 각 spec 본문은 개발자와 리뷰어가 각각 확인합니다. 필요한 테스트 파일을 열지 않고 개발 완료나 리뷰 승인을 제출하면 자동화는 기존 모델·도구 호출 한도 안에서 테스트 읽기와 결과 재제출 기회를 한 번 확보합니다. 수정된 테스트 파일이 있으면 미확인 경로를, 소스만 바뀌었으면 관련 테스트를 고를 수 있는 후보 경로를 안내합니다. 재제출 시에도 확인되지 않으면 대상 경로를 중단 사유에 남깁니다.

수동 수정 때문에 멈춘 초안 PR에서는 수정 내용이 dev에 반영된 뒤 작업 브랜치를 최신 dev로 갱신하고 이슈 번호로 수동 재개할 수 있습니다. 기존 승인 커밋과 최신 dev를 깨끗하게 병합한 파일 트리가 현재 HEAD와 정확히 일치하고 양쪽 이력이 보존된 경우, 기존 승인을 지우고 새 HEAD에서 리뷰와 CI를 진행합니다.

개발 단계가 중단되면 이슈 본문을 유지한 채 수동 재개의 `development_note`로 확인할 파일·테스트의 위치를 전달할 수 있습니다. 개발자는 직전 개발 중단 사유와 메모를 참고해 현재 소스에서 근거를 확인합니다.

같은 커밋에서 보류된 리뷰를 수동 재개하면 리뷰어가 이전 확인 사항을 전달받아 다시 검토합니다. 수동 재개의 선택 입력 `review_note`로 오류 재현 조건을 전달하면 리뷰어가 현재 코드에서 확인합니다. 개발자와 리뷰어는 공통 도우미 `e2e/github.ts`와 고정 응답 `e2e/fixtures.ts`를 읽어 UI 검사의 기대값을 실제 테스트 데이터와 대조할 수 있습니다.

현재 PR 커밋의 CI가 실패하고 소스 또는 UI 테스트 위치가 담긴 오류가 있으면, 완료 워크플로가 해당 오류를 개발자에게 전달합니다. 이슈당 한 차례 자동 수정을 시도하고 새 커밋의 리뷰와 CI를 다시 확인합니다. 포맷 검사만 실패한 기존 PR은 모델 수정 횟수와 별도로 한 번, 개발 모델을 호출하지 않고 해당 PR에서 변경한 편집 가능 파일에만 Prettier를 적용한 뒤 다시 리뷰합니다. 포맷 외에 수정할 코드 위치가 확인되지 않은 실패는 이슈를 `needs_human` 상태로 전환하고 실패한 검사와 CI 실행 링크를 남깁니다. 취소된 실행은 자동 수정 대상에서 제외합니다.

CI 수정으로 새 커밋이 게시되면 리뷰어는 그 커밋의 변경을 새로 검토합니다. 이전 CI 오류는 복구 개발 단계에만 전달합니다. CI 수정 커밋에서 정식 수정 요청이 나오면 해당 커밋에 대해 후속 개발을 한 번 허용하며 일반 리뷰 수정 횟수는 초기화하지 않습니다.
